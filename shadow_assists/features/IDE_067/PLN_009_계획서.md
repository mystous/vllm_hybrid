# CPU–GPU 서빙 노드 전체 성능 개선 연구계획
## 요청 실행·호스트 자원·데이터 준비를 연계하는 공동 실행 제어

**작성일:** 2026-09-12  
**문서 성격:** 연구 범위 및 구현 우선순위 개정. 서버에서 구현할 사항과 사전 확인 사항을 구분한다.  
**적용 관계:** `RBC_Attn_v03_CPU활용_전체성능개선_측정_구현계획_20260912.md`보다 본 문서의 연구 범위·평가 기준을 우선한다. 기존 문서는 RBC를 실제 모델에 적용할 필요가 확인될 때 사용하는 하위 모듈 개발 지침으로 보존한다.  
**최종 목표:** 같은 모델·품질·서버 자원에서 CPU의 적극적인 실행계획 계산과 자원 조정으로 전체 서빙 처리량 또는 요청 지연을 개선한다. 특정 커널이나 특정 sparse mask의 가속을 최종 성과로 대신하지 않는다.

---

## 0. 결정 사항

연구 단위를 **attention 연산자 한 번의 호출**에서 **한 서빙 노드의 요청 처리 과정**으로 확대한다. 처음부터 대규모 분산 시스템을 만들지는 않는다. 한 노드에서 요청 도착, CPU 준비, 데이터 이동, prefill, decode, 응답까지 연결해 동일 정책이 여러 모델과 부하에서 작동하는지 검증한다.

RBC의 타일 크기·비트셋·descriptor 세부 최적화는 주력 작업에서 내린다. 이미 확보한 코드와 검증 결과는 보존하되, RBC가 성공해야 전체 연구가 성립하는 구조를 만들지 않는다.

성능 개선 폭은 일률적인 10% 통과선보다 **서비스 전체의 순이득, 적용 범위, 재현성, 기전의 독립성**으로 평가한다. 예를 들어 사전에 정한 복수 모델·부하에서 전체 지연이나 정상 처리율이 3~5% 안정적으로 개선돼도 후속 평가를 진행할 수 있다. 이는 새로운 연구 단계의 진행 기준이다. 과거 RBC v0.1/v0.2의 실패 판정을 소급 변경하지 않는다.

**금지 사항:** CPU 사용률 자체를 목표로 삼기, 양자화·압축·품질 변경으로 효과 대체하기, baseline의 비동기 실행이나 캐시 기능을 끄기, 존재하지 않는 미래 token·routing을 알고 있는 것으로 처리하기, 여러 기존 옵션을 켠 결과를 새로운 알고리즘의 성과로 합산하기.

## 1. 기존 자료로 확인된 범위와 새 연구 가설

### 1.1 기존 자료

`FULL_REPORT.md`의 E4에서는 GPU-origin의 새 sparse mask를 처리하는 18개 비교 모두 Q-outer보다 전체 시간이 길었다. 작은 형상 일부에서는 GPU 실행시간이 줄었으나, CPU 준비를 포함한 해당 연산자의 완료시간 개선으로 이어지지 않았다. 이는 **RBC의 현재 실행 단위에서 발생한 결과**이지, 실제 서빙 노드 전체에 CPU 활용 기회가 없다는 증거가 아니다. [I1]

`RAW_DATA.md`의 런 99와 100은 같은 Llama-3.1-8B, 요청률 8, 입력 2048/출력 512 조건에서 다음 차이를 기록한다. 이 값들은 원시 표의 개별 실행 관측이며 반복 측정에 의한 유의성 판정은 아니다. [I2]

| 런 | 출력 처리량 | 평균 TPOT | 평균 TTFT |
|---|---:|---:|---:|
| `24_mixed_mnbt512` | 3532.52 tok/s | 19.65 ms | 406.24 ms |
| `24_mixed_off` | 3495.90 tok/s | 24.16 ms | 143.41 ms |

처리량·토큰 간 지연·첫 응답 지연은 같은 방향으로 움직이지 않는다. 이것은 어떤 고정 옵션이 항상 우월하다는 근거가 아니라, **요청의 단계와 자원 상태를 함께 보는 제어 문제를 검토할 동기**다. 새 제어기가 이 두 실행보다 빠르다는 결과는 아직 없다.

### 1.2 새 연구 가설

> CPU가 요청별 준비 완료 시각과 CPU·GPU·데이터 이동의 공통 자원 제약을 함께 계산하면, 단계별로 따로 결정하는 정책보다 유휴·간섭·준비 지연을 줄일 수 있다.

이것은 검증할 가설이다. 현재 자료에 없는 node-level 대기 시간, 공유 DRAM 경합, 실제 KV transfer 대기량을 확정 사실로 전제하지 않는다. 필요한 지표만 먼저 측정하고, 유효한 제어 축부터 구현한다.

## 2. 연구 범위

### 2.1 최적화 대상

| 범위 | 제어할 항목 | 이번 단계의 경계 |
|---|---|---|
| 요청 실행 | 준비가 끝난 요청 중 다음 batch의 구성, prefill 투입량, 요청별 대기 한도 | 기존 엔진의 허용된 배치·청크 실행 경계만 사용 |
| CPU 자원 | 실행계획 계산, 입력·metadata 준비, 기존 CPU expert 작업 사이의 코어·작업 예산 | 총 코어 수 고정. 실제 CPU expert가 없는 모델에 불필요한 expert 연산을 만들지 않음 |
| 데이터 준비 | 현재 요청에 필요한 KV·activation의 전송 순서와 동시 발행량 | 기존 경로가 지원하는 이동만 제어. KV를 일부러 offload하지 않음 |
| GPU 실행 | 다음 실행이 입력·메모리를 기다리지 않도록 배치와 준비 일정을 결합 | Tensor Core 커널, weight/KV dtype, 원래 모델 의존성 유지 |
| 메모리 | 실제 사용 중인 KV·workspace·in-flight 버퍼의 예산 예약 | weight 재배치·동적 압축·무제한 사전 적재는 범위 밖 |

핵심 알고리즘은 하나다. **다음 batch의 선택과 그 batch를 실행 가능하게 만드는 CPU·전송 준비를 같은 일정으로 결정한다.** 항목별로 별개의 최적화 프로젝트를 늘리는 것이 아니다.

### 2.2 CPU의 기여

CPU는 단순 통계 수집이나 API 중계만 담당하지 않는다. 준비된 요청들에 대해 몇 개의 실행 후보를 계산하고, 각 후보의 준비 완료와 자원 충돌을 예측해 실행 결정을 바꾼다. 이 계산으로 실제 전체 성능이 바뀌는지를 검증한다.

하이브리드 MoE 환경에서는 CPU가 기존 expert 수치 연산도 계속 수행한다. 새 제어기의 계산이 expert 워커·NUMA 대역폭·GPU 제출 스레드와 경쟁하는 비용을 반드시 포함한다.

### 2.3 마이크로아키텍처의 위치

마이크로아키텍처는 독립적인 작은 개선항목이 아니라 **노드 수준 실행 결정을 위한 비용정보**로 사용한다.

| 자원 특성 | 상위 정책에 반영하는 방식 |
|---|---|
| CPU NUMA와 실효 DRAM 대역폭 | 어떤 준비·전송·expert 작업을 동시에 허용할지 결정 |
| CPU 캐시 및 코어 경쟁 | 큰 planning 작업과 짧은 GPU 제출 경로의 자원 분리 |
| PCIe 경로와 DMA 동시성 | 단순 bytes/bandwidth가 아닌 현재 큐를 포함한 준비 완료 시각 계산 |
| GPU HBM·workspace | batch를 선택하기 전에 in-flight 메모리까지 예약 |
| GPU 연산 형상·graph 지원 범위 | batch를 지나치게 쪼개거나 graph 밖 형상을 선택하는 비용 반영 |
| TP 통신 | 모든 rank의 공통 실행 순서 유지. rank별 독립적인 batch 재정렬 금지 |

이 항목들은 측정 대상이다. 제품 peak 사양을 현재 서버의 실효 서비스율로 대입하지 않는다.

## 4. 알고리즘: 준비 완료와 자원 예약을 결합한 배치 선택

### 4.1 상태와 행동

현재 시점에 확인할 수 있는 상태만 사용한다.

- 요청: 도착 시각, 서비스 등급, prefill 잔여 길이, decode 진행 상태, 현재 KV 위치, 입력·metadata 완료 여부.
- 자원: NUMA별 실제 가용 코어, CPU 작업 큐, 전송 중인 바이트와 순서, GPU in-flight 작업, KV 및 workspace 예약량.
- 비용: 측정된 batch/phase별 실행시간, 준비 작업시간, 전송시간, 동시 실행 시 지연 변화와 예측 불확실성.

다음 1~2개의 실행 구간을 평가하는 것으로 시작한다. 실제 토큰이 아직 없으면 수치 계산이나 routing을 시작하지 않는다. 알려진 shape·기존 KV 위치·이미 도착한 요청의 metadata만 미리 준비한다.

첫 구현의 행동 집합은 작게 유지한다.

| 행동 | 실제 변경 |
|---|---|
| `native` | 기존 엔진이 선택한 batch와 준비 순서 그대로 |
| `ready_first` | deadline/공정성을 유지하면서 실제 준비가 빠른 요청을 우선 사용 |
| `phase_budget` | 알려진 대기 요청 안에서 prefill 청크 투입량만 제한적으로 변경 |
| `transfer_budget` | 기존 전송 순서·동시 발행량과 다음 batch를 함께 조정 |
| `cpu_budget` | 기존 워커 풀의 허용 범위 내에서 준비/계획/expert 작업의 예산 변경 |

모든 행동의 조합을 전수 탐색하지 않는다. 처음에는 `native`와 추가 후보 2~4개만 비교하고, 실제 이득이 있는 축부터 확장한다. 실행 중 매번 threadpool을 생성하거나 환경변수를 바꾸는 방식은 사용하지 않는다. 워커 예산을 안전하게 변경할 API가 없으면 첫 구현에서는 고정하고 전송·batch 축만 사용한다.

### 4.2 평가 방법

각 후보의 비교 대상은 GPU kernel 하나가 아니라 동일한 대기 요청 집합이다. horizon 안에서 실행하지 않은 요청도 지연 비용에 포함한다. 적은 요청을 골라 처리하고 나머지를 평가에서 빼는 방식은 금지한다.

후보는 다음 순서로 평가한다.

1. 메모리 용량·의존성·실행 지원 조건을 만족하지 않는 후보를 제거한다.
2. 이미 약속한 decode/TTFT 목표와 최대 대기 한도를 고려한다.
3. 남은 후보 중 요청 완료·다음 토큰 도착의 예상 지연과 전체 준비비가 작은 후보를 선택한다.
4. 예측 차이가 불확실성보다 작으면 기존 결정을 유지한다.

아래 식은 단순화한 핵심 관계다. 실제 구현은 선행 관계가 있는 단계별 완료 시각을 계산한다.

\[
F_b(a)=\max\{t_{\rm GPU\ slot},\ t_{\rm ready}(b,a)\}+T_{\rm GPU}(b,a).
\]

여기서 \(t_{\rm ready}\)는 CPU와 전송 시간을 무조건 합산하거나 최대값으로 대체하지 않는다. CPU→DMA→GPU처럼 의존하는 경로는 순차로, 서로 독립적인 경로는 중첩으로 계산한다. 하이브리드 MoE의 forward 내부 fork/join 비용은 별도의 측정된 batch 실행 비용으로 포함한다.

CPU expert와 DMA가 공유 DRAM을 쓰는 경우, 둘의 단독 대역폭을 동시에 보장된다고 가정하지 않는다. 실제 동시 실행의 서비스율을 사용한다. 이 간섭이 작게 측정되면 관련 항을 단순화한다.

### 4.3 준비와 실행의 공동 예약

다음 GPU 실행 기회에 맞춰 필요한 CPU 작업, 데이터 이동, KV/workspace를 함께 예약한다. 예약은 CPU planning 결과일 뿐이며, GPU의 실제 실행 시작은 원래 event와 메모리 유효성 검사로 확인한다.

데이터를 지나치게 일찍 올려 HBM을 오래 점유하는 것과, 너무 늦게 준비해 GPU를 기다리게 하는 것 사이를 조정한다. 요청 종료 길이를 미리 아는 것으로 처리하지 않는다. 현재까지의 진행량과 다음 실행 구간에 실제 필요한 추가 메모리를 기준으로 예약한다.

준비가 예상보다 늦어지면 메모리·작업 예약을 갱신하고 가능한 기존 경로를 사용한다. 미래 완료시각 예측을 근거로 미완료 텐서를 소비하지 않는다.

### 4.4 의사코드

```text
on existing_engine_boundary_or_resource_event:
    state = read_incremental_state()          # 매번 전체 큐·tensor를 재구성하지 않음
    native = original_scheduler.propose(state)

    if no_eligible_control_opportunity(state):
        execute(native)
        return

    candidates = build_small_candidate_set(native, state)
    best = native
    for candidate in candidates:
        if not feasible_with_inflight_memory(candidate, state):
            continue
        estimate = forecast_cpu_dma_gpu(candidate, state)
        if improves_request_objective_with_margin(estimate, best):
            best = candidate

    reserve_preparation_and_execution(best)
    dispatch_only_dependency_ready_work(best)
    update_models_from_completion_events()
```

비용 예측과 제어기 자체의 실행시간도 측정한다. 이 제어기를 매 attention 호출마다 실행하지 않는다. 처음에는 엔진 batch 경계와 실제 자원 상태가 달라진 사건에서만 실행한다.

### 4.5 예상되는 이득의 형태

예를 들어 GPU에 들어갈 다음 요청의 KV 이동을 먼저 시작했지만, 같은 NUMA의 CPU expert 읽기와 경쟁해 현재 decode가 늦어질 수 있다. 이 경우 전송을 잠시 늦추는 일정이 전체 토큰 간격을 줄일 수 있다. 반대로 현재 작업이 GPU에서 충분히 오래 실행되고 호스트 자원이 비어 있으면 다음 요청의 데이터와 metadata를 미리 준비하는 것이 유리할 수 있다.

이 예시는 **판별할 상황**이며 현재 서버에서 그런 간섭이 측정됐다는 주장이 아니다. 두 경우를 같은 '항상 overlap' 또는 '항상 직렬' 정책으로 처리하지 않는 것이 제안 규칙의 목적이다.

## 5. 선행연구와의 관계 및 논문 기여

CPU 스케줄링, prefill/decode 혼합, KV-aware 실행 자체는 기존 기술이다. 다음 자료와의 직접 비교를 유지한다.

| 기존 기술 | 확인된 내용 | 이번 연구가 추가로 입증해야 하는 것 |
|---|---|---|
| vLLM async scheduling | CPU scheduling과 GPU 실행의 중첩을 위한 동시 batch 관리 [R1] | 비동기 실행이 켜진 기존 엔진에서도 공동 예약 규칙의 추가 이득 |
| Sarathi-Serve | chunked prefill과 stall-free scheduling을 통한 처리량·지연 조정 [R2] | prefill/decode 배치 선택만으로 얻는 효과와 CPU·전송 준비 결합 효과의 분리 |
| MemServe | KV/context cache와 disaggregated 실행을 연계하는 메모리·스케줄링 구조 [R3] | 이미 cache-aware인 경로 대비 준비 시각·호스트 자원 경쟁을 고려한 의사결정 차이 |
| HybriMoE | CPU–GPU 계층 내 스케줄링, inter-layer prefetch, expert cache 정책 [R4] | expert별 장치 선택을 그대로 반복하지 않고 요청 전체와 공유 자원에 대한 추가 제어 효과 |

공식 설명·논문 초록에서 확인되는 범위로 정리했다. 이 표만으로 모든 최신 선행과의 중복 검토가 끝났다고 보지 않는다. 새 정책을 핵심 기여로 확정하기 전, 구현된 결정 규칙과 가장 가까운 기존 정책을 코드/의사코드 수준에서 대조한다.

**논문 기여 후보:** 요청별 준비 완료와 CPU·전송·GPU 사용을 결합한 실행 결정, 그 결정을 뒷받침하는 제한된 관측 비용의 자원 모델, 서로 다른 추론 경로에서 같은 규칙의 실효성을 보이는 평가.

여러 기존 기능을 한 시스템에 연결한 사실이나 조정할 옵션 수는 신규성의 근거가 아니다. 기존 독립 제어와 공동 제어가 실제로 다른 결정을 내리는 사례와 그 차이의 순이득을 제출해야 한다. 3~5% 개선은 후속 검증을 진행할 수 있는 성과 규모이지, 그 자체로 논문 채택이나 신규성을 보장하는 수치가 아니다.

## 6. 필요한 측정과 구현 순서

### 6.1 선행 측정 M0 — 전체 실행 경로 한 번 연결

대상은 현재 운영 가능한 안정적인 엔진 1개와 모델 1개다. `RAW_DATA.md`에서 이미 실행한 Llama-3.1-8B/vLLM 조합을 첫 후보로 삼되, 서버에 같은 버전·모델이 실제로 준비돼 있는지 확인한다. 모델을 바꾸면 그 이유와 기준선을 남긴다.

낮은 부하, 용량에 가까운 부하, 긴 입력이 섞인 burst의 세 경우만 먼저 본다. full profiler를 장시간 켜지 않는다. 요청·batch ID에 다음 event를 연결한다.

| 단계 | 필수 정보 |
|---|---|
| 요청 | 계획 도착/실제 전송/서버 접수 시각, 입력 길이, 출력 상한 |
| 준비 | CPU 준비 시작·종료, 데이터 위치, 필요한 전송, 대기 원인 |
| GPU | batch ID, prefill/decode 토큰 수, GPU 실제 시작·종료, graph 경로 |
| 메모리 | KV·workspace·in-flight 예약량, 회수·재계산 여부 |
| 응답 | 첫 토큰/후속 토큰/종료·실패 시각 |
| 자원 | 실제 가동 구간의 코어 사용·NUMA/DRAM·DMA·GPU 활동 |

CPU와 GPU의 시간을 직접 빼기 전에 clock domain을 맞추거나 공통 trace 도구로 상관시킨다. 개별 kernel 시간을 합해 임계 경로로 표시하지 않는다. 서버 기동·모델 loading·drain을 정상상태 자원 평균에 섞지 않는다.

**산출물:** 전체 요청 경로에서 회수 가능한 준비 대기·자원 간섭·불필요한 이동의 위치와 크기. GPU가 순수 계산 또는 필수 메모리 처리로 이미 한계인 조건에서는 새 정책의 이득 상한이 작다는 사실도 남긴다.

M0의 목적은 'CPU 사용률이 낮으니 일을 더 주자'가 아니다. 어디의 순서를 바꿔야 다른 요청까지 포함한 완료시간이 줄어드는지 찾는 것이다.

### 6.2 즉시 구현 I0 — 공통 연결부

새 kernel 없이 다음 연결부를 구현한다. 아래 파일명은 제안 구조이며 서버 저장소에 맞춰 조정한다. 기존에 구현돼 있다고 가정하지 않는다.

| 모듈 | 역할 |
|---|---|
| `node_control/state` | 요청·CPU·전송·GPU·메모리의 공통 상태표 |
| `node_control/policy` | native/개별 제어/공동 제어의 같은 인터페이스 |
| `node_control/reservation` | 다음 준비·전송·실행과 메모리의 예약·취소 |
| `node_control/cost` | 실제 형상·간섭 상태의 작은 비용 표와 오차 기록 |
| `node_control/trace` | 결정과 실제 결과의 대응 로그 |
| `adapters/vllm` 또는 `adapters/sglang` | 현재 설치된 엔진의 실제 실행 경계에 연결 |

I0에서 새 정책을 끈 상태가 baseline과 같은 결과를 내는지 먼저 확인한다. 호환되지 않는 private API를 추측해서 patch하지 말고, 실제 버전에서 source map을 작성한다.

### 6.3 I1 — 하나의 실효적인 공동 제어 축

M0에서 관측된 기회에 따라 `batch+CPU 준비` 또는 `batch+실제 데이터 이동` 중 하나로 시작한다. 둘 다 이득 가능성이 없으면 억지로 기능을 추가하지 않는다.

처음에는 shadow mode로 기존 결정을 바꾸지 않고 후보와 예상 결과를 기록한다. 이어 native와 새 결정을 번갈아 적용하는 replay/실행 비교로 확인한다. 오프라인 trace의 미래 정보를 온라인 정책에 주지 않는다.

### 6.4 I2 — 하이브리드 수치 연산과 일반화

첫 엔진에서 의미 있는 이득이 확인되면 CPU expert를 실제로 수행하는 안정적인 hybrid 모델에 같은 정책 인터페이스를 연결한다. 480B에서 이미 보고된 NaN을 단순 치환해 정상 실행으로 처리하지 않는다. 정상성 검증이 된 구성이나 별도 안정 모델에서 시작한다.

이 단계에서 CPU controller가 원래 CPU 연산을 방해하는 비용까지 포함한다. 데이터 배치와 정밀도를 바꿔 정책의 이득을 만들지 않는다.

### 6.5 RBC의 사용 조건

실제 모델에 원래 존재하는 sparse attention의 준비가 전체 성능에 영향을 미치는 경우만 RBC를 하위 실행 후보로 연결한다. 그렇지 않으면 RBC가 빠져도 전체 정책의 구현·평가를 계속한다. RBC용 합성 mask를 일반 모델에 새로 넣지 않는다.

## 7. 평가 설계

### 7.1 기준선

| 코드 | 비교 경로 | 목적 |
|---|---|---|
| B0 | 현재 최적화한 native 엔진. 지원되는 async·graph·batch·cache 기능 허용 | 실제 시스템 기준 |
| B1 | 새 연결부와 계측만 추가하고 native 결정 유지 | 프레임워크 자체의 비용 |
| B2 | 개별 제어만 적용. CPU 준비/전송/배치를 따로 선택 | '통합했다'는 주장과 실제 공동 결정의 차이 |
| B3 | 같은 자원정보를 쓰는 단순 ready-first 또는 deadline 정책 | 복잡한 정책이 필요한지 확인 |
| P | 준비 완료·자원 예약을 함께 고려한 새 정책 | 검증 대상 |

같은 CPU core set, GPU 수, NUMA 배치, 모델, precision, cache 한도, 요청열을 사용한다. native에도 후보와 같은 튜닝 기회를 제공한다. 기존 엔진이 지원하지 않는 설정을 런타임에 바꾼 것으로 적지 않는다.

### 7.2 모델·워크로드 범위

한 번에 모든 조합을 수행하지 않는다. M0/I1은 1개 모델로, 일반화는 다음 범주에서 최소 2개 구조로 진행한다.

| 범주 | 목적 |
|---|---|
| GPU에 상주 가능한 dense 모델 | CPU 계획이 일반적인 서빙에도 가치가 있는지 검증 |
| CPU가 실제 수치 계산을 수행하는 hybrid MoE | 제어 비용과 CPU expert 비용의 공존 검증 |
| 다른 GPU 수 또는 다른 모델 크기 | 특정 core·batch 설정에만 맞춘 결과인지 확인 |

부하는 짧은 대화형, 긴 입력, 긴 출력, 길이 혼합, burst 후 정상 부하 복귀로 구성한다. prefix cache는 실제 데이터에 존재하는 hit를 사용하고, cold/warm 조건을 구분한다. 처음부터 수십 개 모델을 도입해 연구의 중심을 흐리지 않는다.

### 7.3 주 지표

주 지표는 사전에 한 가지를 정한다.

- 온라인: 같은 TTFT·토큰 간 지연 목표를 만족하는 **정상 요청 처리율**과 지속 가능한 도착률.
- 고정 작업: 같은 요청 집합의 처음 도착부터 마지막 정상 완료까지의 wall time.

보조 지표는 요청별 TTFT·ITL·TPOT·E2E, 모델 forward 시간, CPU와 GPU의 유효 중첩, 준비 때문에 노출된 GPU 유휴, 메모리 예약·재계산, 에너지 및 controller core-seconds다.

TPOT는 요청 평균 토큰 간격이며 ITL tail과 같지 않다. 공동 SLO는 같은 request ID에서 판정한다. 실패·거부·취소·수치 이상을 집계에서 누락하지 않는다.

### 7.4 반복과 작은 개선의 판정

발견 단계는 5개 독립 도착열/seed를 사용한 paired 비교로 시작한다. 1~5% 수준의 차이가 나타나면 최종 평가에서는 독립 실행을 늘려 신뢰구간을 확인한다. 같은 graph를 수천 번 replay한 값은 수천 개 독립 서빙 실험으로 취급하지 않는다.

신뢰구간은 request를 무작정 독립 표본으로 취급하지 말고 run 단위 pairing 또는 시간 block을 고려해 계산한다. baseline/P 실행 순서를 바꾸고 실험 시작·종료의 온도·클럭·경쟁 workload를 기록한다.

**진행 판단:** 사전에 정한 주 workload에서 반복 가능한 양의 순이득이 있고, 의미 있는 다른 범주에서도 비슷한 경향을 보이면 평가를 계속한다. 3~5%는 허용하는 초기 성과 규모이며, 작다는 이유만으로 폐기하지 않는다. 반대로 넓은 결과를 모두 평균내서 특정 부하의 큰 손해를 숨기지 않는다.

fallback으로 baseline과 같아진 경우는 회귀 방지다. 실제 선택이 바뀌어 순이득이 발생한 요청·batch의 비율과 기여를 따로 보고한다.

### 7.5 전체 성능 기여의 설명

어떤 연산이 전체 실행시간의 10%를 차지하고 그 부분을 20% 줄였다는 가상의 경우, 다른 조건이 같다면 전체 시간 감소는 2%다. 그 결과를 '연산자 20% 가속'으로만 보여주거나, 전체 10%에 못 미친다는 이유로 폐기하지 않는다.

실제 CPU/GPU 실행은 중첩되므로 위 단순 비율을 그대로 사용하지 않는다. 전체 wall과 실행 trace에서 임계 경로가 얼마나 달라졌는지 함께 확인한다.

## 8. 서버 에이전트에게 전달할 실행 지시

> 기존 RBC v0.3의 bitset/descriptor 커널 최적화를 주력으로 계속하지 말라. 기존 소스와 결과는 보존한다. 이번 목표는 실제 LLM 서빙 노드에서 요청 실행과 CPU·데이터 준비를 공동 제어해 전체 성능을 높이는 것이다. 먼저 안정적인 엔진 1개에서 M0의 세 부하만 연결 계측하고, 동시에 native 정책을 그대로 통과시키는 I0 연결부를 만든다. 그런 다음 실제로 확인된 대기·간섭에 대응하는 공동 제어 축 하나를 구현한다. 새 kernel, 새 양자화, sparse mask 도입, weight 재배치, 전체 threadpool 교체는 우선 범위에 넣지 않는다. CPU에 추가 작업을 주었다는 사실이 아니라, 같은 자원·모델·요청에서 전체 완료시간이나 동일 SLO의 정상 처리율이 좋아졌는지를 반환한다. 필요한 통합 소스는 현재 서버의 실제 버전에서 수정하며, 별도 코드 ZIP을 기다리지 않는다.

반환 자료는 다음 네 묶음으로 제한한다.

| 산출물 | 내용 |
|---|---|
| `SYSTEM_RESULT.md` | 주 지표, 기준선, 개선 범위, 손해 범위, 결론 |
| `source_diff/` | 수정 코드, 원래 commit·설정, 공통 연결부와 정책의 구분 |
| `runs/` | 반복별 원본 시간·요청 결과·실패·자원 예산 |
| `decisions/` | 어떤 상태에서 native와 다른 결정을 했고 실제 결과가 어땠는지 |

현재 문서는 구현할 정책과 평가 범위를 정의한 계획이다. 새로운 node-level 알고리즘이 이미 구현됐거나 서버에서 가속됐다고 표시하지 않는다.
