# EXP-E11 구성 선택 비용모델 사양 (IDE_060)

실행계획서 `shadow_assists/brainstorming/epoch_experiment_plan_20260909.md` §17 의 산출물 `selector_spec.md` 에 해당한다.
**선택적 확장이며, EPOCH 의 기존 측정 결과는 이 작업의 성패와 무관하다.**

## 1. 왜 필요한가 (EXP-E10 이 만든 근거)

EXP-E10 에서 고정 구성의 한계가 측정으로 드러났다.

| 워크로드 | 고정 C64 | 각자 최적 C |
|---|---|---|
| 512/128 (보정 워크로드) | EPOCH −1.6% | EPOCH +19.1% |
| 4096/128 (긴 입력) | EPOCH +11.1% | EPOCH +5% 수준 |
| 512/1024 (긴 출력) | **EPOCH −21.4%** | EPOCH +12.7% |

즉 "EPOCH 구성을 그대로 배포" 하면 워크로드에 따라 손해가 난다. 손해를 피하려면 **워크로드마다 구성과 운영 동시성을 고르는 규칙**이 있어야 하고, 그 규칙은 측정 전에 답을 내야 한다. 이 문서는 그 규칙을 정의한다.

FP8 KV·graph 버킷·chunked prefill 은 모두 기존 기능이다. 그 자체를 새 알고리즘이라 부르지 않는다. 여기서 새로 제안하는 것은 **CPU expert 실행 비용과 GPU 메모리 기회비용을 함께 반영해 구성을 고르는 절차**뿐이며, 아직 신규성이 입증된 것으로 취급하지 않는다.

## 2. 모델 구조

측정으로 뒷받침되는 항만 둔다. 구현은 `model/selector.py`.

### 2.1 KV 용량 — 상수표 (측정)

boot 로그 24건에서 KV 풀 토큰 수는 **graph 버킷 수·graph 최대 batch·chunk 크기와 무관**했고 dtype 으로만 결정됐다.

```
N_kv(bf16) = 63,654    N_kv(fp8_e5m2) = 127,309     (mem-fraction-static 0.94, hot-96, TP4)
--max-total-tokens M 이 주어지면 N_kv = min(N_kv, M)
```

이는 SGLang 이 KV 풀을 graph capture 이전에 mem-fraction-static 으로 확정하고, graph 메모리는 그 바깥의 여유에서 쓰기 때문이다. 따라서 "버킷을 늘리면 KV 가 줄어든다" 는 교환은 이 구성에서 성립하지 않는다. graph 메모리는 **부팅 가능/불가능** 의 이산 제약으로만 들어간다.

### 2.2 실행 가능 배치

```
L_avg  = L_in + L_out / 2                       (생성 도중 평균 KV 점유)
B_cap  = eta * N_kv / L_avg
B_eff  = min(C, admission_cap, B_cap)
binding = 셋 중 최소를 준 항 (선택 결과 해석에 사용)
```

### 2.3 디코드 스텝 시간 (ms)

```
pad(B) = B 이상인 가장 작은 캡처 버킷           (B <= graph_max)
T(B)   = t0 + t1 * pad(B) * (rho if B > graph_max else 1) + t2(q) * B * L_avg / 1000
```

`t2` 는 KV dtype 별로 따로 둔다 (attention 이 읽는 KV 바이트가 다르므로).
`rho` 는 graph 를 벗어난 batch 의 eager 실행 벌점.

### 2.4 prefill 몫과 출력 처리량

```
share_decode = (L_out * T/1000) / (L_out * T/1000 + L_in / P)
출력 tok/s   = eps * B_eff / T * 1000 * share_decode
```

`P` 는 prefill 처리량 (tok/s), `eps` 는 램프·스케줄링 등 정상상태 밖의 손실을 담는 보정 상수다. `eps = 0.77` 은 큰 값이며, 모델이 설명하지 못하는 몫이 23% 남아 있다는 뜻이다. 이 값을 물리적 의미가 있는 항으로 쪼개는 것은 후속 과제다.

### 2.5 모델이 다루지 않는 것 (적용 범위)

- **CPU 워커 수**: `--kt-cpuinfer` 96 고정. 48/72 셀 (EXP-E04) 은 범위 밖이고 실제로 18~25% 과대예측된다.
- **실행 패치 해제 (R0)**: 범위 밖 (11~21% 과대예측).
- **mixed forward**: 예측에 항이 없다. 512/128 에서는 우연히 잘 맞으나 (오차 0.4~3.5%) 검증된 것이 아니므로 선택 범위에서 제외한다 (§17.3 지시).
- **KV 초과 구독 (C > B_cap)**: `C2` 셀 (KV 를 63,654 로 제한하고 C224) 에서 실측 630 tok/s vs 예측 929 (+47.5%). 요청 회수(retract) 로 낭비된 작업으로 보이나, 같은 초과 구독인 `G_TUN 4096x128 C64` 에서는 처하락이 없다. 근거가 한 셀뿐이라 **벌점 항을 적합하지 않고**, 대신 `oversub = C/B_cap − 1` 을 위험 표식으로 출력해 선택에서 회피한다.
- **job 크기 < 3×C**: 램프 구간이 지배한다 (`G_EPO 512x1024 C64`, np=128 → 실측 438 vs 예측 614). 보정에서 제외했고, 평가 측정도 np ≥ 3C 로 한다.

후보 공간 밖인 graph_max 96 에서만 측정해 held-out 오염을 피했다. 10 셀.

**(a) 그래프 밖 실행 벌점 — 가장 큰 단일 효과**

|---|---|---|

| 128 (그래프 밖) | 424.17 (**−51.0%**) / 269.3 | 432.31 (**−50.2%**) / 260.5 |

동시성이 `--cuda-graph-max-bs` 를 넘으면 처리량이 절반이 된다. 두 chunk 구성에서 독립적으로 재현.
이 셀이 있기 전에는 `rho` (그래프 밖 벌점) 를 뒷받침하는 측정이 **하나도 없었다**. 적합값은 4.95 가 됐다.

**(b) chunk 크기**

|---|---|---|---|
| 512/128 C64 | 772.52 | 778.19 | +0.7% (반복 변동 안) |

짧은 입력에서는 처리량 차이가 없고 TTFT 만 나빠지며, 긴 입력에서만 3~5% 이득이다.

**한계 (정직하게 기록)**: 적합 결과의 `P4096` (652) > `P8192` (544) 는 위 직접 측정의 방향과 반대다.
prefill 항이 단일 상수 P 로 표현돼 있어 "chunk 가 커지면 여러 요청의 prefill 을 한 배치로 묶어
GPU 이용률이 오른다" 는 실제 기전을 담지 못한다. chunk 축의 예측은 **약하게 식별된 상태**이며,
held-out WH2 (3072/256) 에서 선택이 틀리면 regret 으로 드러난다. 이 상태 그대로 사전등록한다.

## 4. (해소됨) 아직 보정되지 않았던 축

후보 공간 (§17.2) 은 `graph_max ∈ {160,192,224} × 버킷 간격 {16,32} × chunk {4096,8192}` 12개다. 그런데 현재 모델은

- **chunk** 를 구분하지 못한다 (`P` 가 상수). → 1단계에서 chunk 8192 보정 boot 로 `P(chunk)` 를 만든다. 보정 boot 는 후보가 아닌 `graph_max 96` 에서 수행해 held-out 오염을 피한다.
- **버킷 간격** 은 `pad(B)` 로만 들어간다. C 가 버킷 값과 일치하면 두 간격이 동일한 예측을 낸다. 따라서 평가는 `B_eff` 가 버킷 사이에 떨어지는 (KV 제약이 binding 인) 지점을 반드시 포함한다.

## 5. 학습·평가 분리

`calibration_split.json` 에 명시한다.

- **보정 (calibration)**: 512/128 (sonnet), 4096/128 (sonnet), 512/1024 (sonnet, np≥3C 인 셀만). 2026-09-10 이전 측정.
- **held-out**: `random` 데이터셋 2048/512. 입력 길이·출력 길이·토큰 분포가 모두 보정에 없는 조건이다. hot map 은 held-out 워크로드에서 다시 학습하지 않는다 (α=0.25 mixed map 그대로).

## 6. 선택 목적과 비교 정책

```
x* = argmax  예측 출력 처리량(x, w)
     s.t.    부팅 가능 (graph 메모리)
             oversub(x, w) <= 0.1
             예측 TPOT <= SLO
```

| 정책 | 정의 |
|---|---|
| 고정 EPOCH-B | 최종 B 구성을 모든 워크로드에 사용 |
| memory-only | KV 용량이 가장 큰 구성 (fp8 + 최대 max-total-tokens) |
| 단일요인 탐색 | graph_max → 간격 → chunk 순차 조정, 같은 측정 예산 |
| 무작위 탐색 | 같은 측정 예산으로 후보 무작위 |
| **비용모델 선택** | 위 목적함수 |
| 전수탐색 oracle | 12 후보 전부 측정한 사후 최선 (온라인 정책 아님) |

```
selection_regret = (Y_oracle − Y_selected) / Y_oracle
```

목표: held-out regret 중앙값 ≤5%, 최악 ≤10%, 안전 제약 위반 0. 탐색 비용 (boot 수, GPU wall time, profile 수) 도 정책별로 함께 보고한다.

## 7. 판정

모든 held-out 워크로드에서 고정 B 가 이미 최적이고 비용모델의 이득이 없으면, 선택 알고리즘 주장을 추가하지 않고 그대로 기록한다.
