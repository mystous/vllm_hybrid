## 1. 기반 이론 — 그리고 무엇이 새로운가

### 1.1 출발 사실 (기존 지식, 신규성 아님)

CPU 에 상주한 MoE expert 의 연산은 **memory-bound** 다. expert e 가 한 스텝에 처리하는 토큰 수를 `n_e` 라 하면:

```
T_cpu(e) ≈ max( W_e / BW_dram ,  6·h·m·n_e / C_cpu )      (roofline)
           └─ weight 1회 읽기 ─┘  └─ 3 GEMM 연산 ─┘
W_e = 3·h·m·b   (gate/up/down, b = bytes/param)
```

`n_e` 가 작으면 왼쪽 항(weight 읽기)이 지배 → **토큰당 비용 = W_e/(BW·n_e) ∝ 1/n_e**. 여기까지는 CoX-MoE 등도 아는 사실이다 (그래서 그들은 micro-batch 를 ordinary-batch 로 합친다).

### 1.2 신규 관찰 ① — speculation 은 n_e 의 증폭기다

검증(verify) 스텝의 토큰 수는 `T = M·(K+1)` (M = 배치 요청 수, K = spec depth). top-k 라우팅 (E 개 중 k 개) 에서 기대값:

```
n_e ≈ T·k/E = M·(K+1)·k/E
```

**즉 K 는 모든 expert 의 n_e 를 (K+1)배 증폭하는 소프트웨어 다이얼**이다. 기존 문헌에서 K 는 ① 지연 단축 (Leviathan 계보) ② 전송 은닉 (2508.21706) 수단이었고, **"CPU 연산의 arithmetic intensity 를 조종하는 배치 제어변수"로 본 논문은 없다** (CoX-MoE: no-spec, FASER/TurboSpec/AdaSpec: GPU-only 비용모델).

### 1.3 신규 관찰 ② — "투기 낭비는 memory-bound 구간에서 공짜다" (핵심 정리)

GPU-only spec 의 근본 비용은 **기각된 draft 토큰의 검증 FLOPs 낭비**다 (α 낮으면 손해 — FASER 류가 K 를 줄이는 이유). 그런데 CPU-상주 expert 는 memory-bound 구간에서:

```
스텝당 CPU 비용 ≈ (touched experts 의 weight 총량)/BW   — n_e 에 거의 무관!
```

expert 전 집합이 touch 되는 지점 (`T·k ≳ E·ln E` 근방) 이후로는 **K 를 더 올려도 weight 읽기 총량이 늘지 않는다** → 기각될 토큰을 몇 개 더 검증하는 한계비용 ≈ 0. 따라서:

> **정리 (예측): goodput-최적 spec depth 는 CPU-hybrid 에서 GPU-only 보다 크다 (K*_hybrid > K*_gpu).**
> 직관: GPU-only 에선 낭비가 비싸고, CPU-hybrid 에선 낭비가 거의 공짜이므로 더 공격적으로 투기하는 것이 최적이 된다.

이것이 본 논문의 **검증 가능한 반직관 예측**이며, 어떤 선행 연구도 제시하지 않았다.

### 1.4 신규 관찰 ③ — knee 닫힌형과 dispatch 경제 규칙

roofline 교차점 (memory→compute 전환):

```
n* = b·C_cpu / (2·BW_dram)
```

prod 노드 대입 (SPR×2, 지속 C_cpu≈70 TFLOPS bf16-AMX, BW≈400 GB/s 지속):
- AMXINT4 (b=0.5): **n* ≈ 44 tokens/expert**
- AMXINT8 (b=1): **n* ≈ 88 tokens/expert**

n_e < n* 인 expert 는 CPU 에서 "추가 토큰 공짜" 구간 → CPU 배치가 유리. n_e 가 큰 hot expert 는 GPU 상주가 유리. **per-step, per-expert 의 위치 결정이 (K, α, routing skew) 의 함수로 닫힌형이 된다** — 정적 stratification (CoX-MoE) 과 달리 K 와 공동 최적화되는 동적 규칙. 이 (K, placement, deferral) 공동 최적화가 시스템 기여.

### 1.5 수치 예시 (DeepSeek-R1-0528, 이론 계산 — 실험 아님)

E=256 routed (k=8), 58 MoE layers, W_e(int4) ≈ 22MB, BW=400GB/s 가정:

| 구성 | T (토큰/스텝) | touched experts/layer | weight 읽기/스텝 | 수락 토큰/스텝 (α=0.5) | 이론 throughput |
|---|---:|---:|---:|---:|---:|
| M=64, **K=0** | 64 | ~222 | 222×22MB×58 ≈ 283GB | 64 | ~90 tok/s |
| M=64, **K=7** | 512 | ~256 (포화) | 256×22MB×58 ≈ 327GB | 64×4.5 = 288 | **~352 tok/s** |

→ weight 읽기는 **+15%** 만 늘고 수락 토큰은 **4.5×** — 같은 DRAM 대역폭에서 **~3.9× throughput**. (참고 sanity: 이 모델은 우리 8-27 실측 19.7 tok/s (M=8, K=0, turbo off) 와 오더 일치)

### 1.6 신규성 요약 (3개 주장)

1. **식별**: spec depth K = CPU expert 배치 경제성의 1급 제어변수 (최초)
2. **이론**: "투기 낭비 공짜" 정리 + knee 닫힌형 + **K* 이동 예측** (최초, 반증 가능)
3. **시스템**: (K, expert 배치, deferral) 을 단일 goodput 최적화로 푸는 온라인 제어기 + 서버급 (2S-SPR AMX + H100×8) 최초 실증

## 2. 기대하는 바 (정량 가설 — 사전 등록)

| # | 가설 | 정량 예측 | 반증 조건 |
|---|---|---|---|
| H1 | roofline knee 실재 | AMX expert GEMM 의 tokens/expert-시간 곡선이 n*≈44 (int4) / 88 (int8) ±50% 에서 꺾임 | 곡선이 전 구간 선형 (knee 부재) |
| H2 | 투기 낭비 공짜 | expert 전 집합 포화 후, 스텝당 CPU expert 시간의 K-기울기 ≤ 0.15×(선형 기울기) | 기울기 ≥ 0.5×선형 |
| H3 | **K* 이동** (핵심) | 동일 워크로드에서 argmax_K goodput: hybrid 가 GPU-only 보다 **≥ +2** 크게 나옴 | K* 차이 ≤ 0 |
| H4 | e2e 이득 | capacity-exceeded MoE serving 에서 no-spec KT 대비 **2~4×** decode throughput (α≈0.5 워크로드) | < 1.3× |
| H5 | 동적 dispatch | 정적 stratification (CoX-MoE 방식 재현) 대비 +10~30% (routing drift 워크로드) | ≤ +5% |
| H6 | α-경계 (regime 정직성) | α < ~0.1 (code 류) 에선 이득 소멸 — 모델이 예측하는 경계와 실측 일치 | 경계 예측 오차 > 2× |

**실패해도 논문이 되는 구조**: H3 가 기각되면 "왜 이동하지 않는가" 의 병목 규명 (제어 오버헤드, ragged-batch 등) 자체가 특성화 기여로 전환 — 사전 등록형 서사.

## 3. 실험 절차 (E0 → E5, 의존 순서)

### E0 · 이론 검증 시뮬레이션 — **지금 실행 가능 (하드웨어 불요)**
1. §1 비용모델을 Python 시뮬레이터로 구현 (E, k, M, K, α, skew, BW, C 파라미터화)
2. 8-27 실측치 (R1 19.7 tok/s, Qwen 96.1 tok/s) 로 모델 캘리브레이션 (BW_eff, C_eff 역산)
3. H3/H4/H6 의 예측 수치표 산출 → 이후 실측과 대조할 사전 예측 고정
- 산출물: `sced_sim.py` + 예측표. **GPU/CPU 부하 없음 — 타 실험과 무충돌**

### E1 · AMX expert microbench (H1) — CPU only, ~2h 점유
1. kt-kernel 의 AMXINT4/INT8 expert GEMM 을 단독 호출하는 하네스 작성
2. n_e ∈ {1,2,4,…,512} sweep × dtype × NUMA 배치 → 토큰당 시간 곡선
3. knee 실측 vs n* 닫힌형 비교
- 통제: turbo 상태 고정 명시, 코어수 고정, 3-run

### E2 · K-증폭 실측 (H2) — GPU+CPU, ~반나절
1. SGLang+KT 스택 (8-27 구축분) 에 per-step 계측 추가: expert 별 n_e 분포, 스텝당 CPU expert 시간
2. 고정 워크로드에서 K ∈ {0,1,3,5,7,10} sweep (Qwen3-30B-A3B — 품질 정상 확인된 모델; draft = 소형 동계열)
3. "스텝당 CPU 시간 vs K" 곡선의 평탄성 측정 (H2), touched-expert 포화점 확인

### E3 · K* 이동 실증 (H3, 핵심 실험) — ~1일
1. 두 시스템: (a) GPU-only + spec (vLLM/SGLang 표준), (b) CPU-hybrid + spec (동일 draft)
2. 동일 워크로드 α 3수준 (chat≈0.8 / sonnet≈0.4 / code≈0.01 — 5월 실측 재사용) × K sweep
3. goodput(K) 곡선 두 벌 → argmax 비교. **논문 Figure 1 후보**

### E4 · 동적 dispatch vs 정적 (H5) — ~1일
1. dispatch 정책 3종 구현: all-CPU (KT 기본) / 정적 빈도 stratification (CoX-MoE 재현) / **SCED 동적 (n_e 임계 규칙)**
2. routing drift 워크로드 (도메인 전환 시나리오) 에서 비교

### E5 · e2e + SLA (H4, H6) — ~2일
1. capacity-exceeded 본판: R1-0528 (SUB_167 해결 시) 또는 후속 대형 MoE
2. baselines: KT no-spec / KT+수동 K / SCED 제어기. TPOT SLA 제약하 goodput
3. ablation: turbo on/off (사용자 승인 시), NUMA, deferral 유무

**총 GPU 점유 예상 ~4일 (E1~E5). E0 는 즉시, 나머지는 실행 허가 대기.**

## 4. 판정 (게이트)

- **논문 go**: H1·H2·H3 모두 성립 (이론 3요소 실증) — H4 배율은 크기와 무관하게 정직 보고
