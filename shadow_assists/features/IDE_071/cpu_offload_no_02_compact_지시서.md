# CPU MoE Offloading 후속 실험 지시서 — 실행량 제한형

> 문서 ID: `cpu_offload_no_02_compact`  
> 근거: 사용자 제공 `FULL_REPORT.md`의 IDE_069, `RESULT.md`의 IDE_070.  
> 목적: 기존 구현과 설치된 설정만으로 C64 성능을 추가 탐색한다. 원인 규명 연구·새 커널 개발·대규모 검증을 한 캠페인에 포함하지 않는다.  
> **이 문서는 이전 `cpu_offload_no_02_실험계획_지시서.md`의 실행 범위·반복 수·수렴·완료 조건을 대체한다. 이전 12단계를 추가로 실행하지 마라.**

## 1. 필수 실행 원칙

1. **서로 다른 서버 구성 최대 8개, 일반 성능 벤치 최대 20회**로 제한한다. 진단 1회, 연속 부하 1회, 복구 재시도 2회를 포함해 성능·진단 부하 실행은 최대 24회다. 준비·출력 확인은 제4절의 별도 상한을 적용한다.
2. 탐색 후보는 먼저 1회씩만 측정한다. 확인 대상으로 선정된 최대 2개 구성만 별도의 3회 반복을 수행한다. 1회 수치를 확정된 개선 효과로 표현하지 않는다.
3. 성능이 낮거나 개별 셀이 실패해도 전체 캠페인을 포기하지 마라. 제한된 복구 후 다음 독립 항목으로 이동하고, **이번 문서의 유한한 범위와 데이터 저장·게시·전달까지 완료하라.**
4. **실험 시작 후 30분마다 중간 보고하라.** 보고 때문에 실행 중인 벤치를 중단하지 마라. 이 요구는 실제 실험 실행자의 보고 루프에 대한 지시이며, 문서 작성 자체가 실험이나 알림 서비스를 실행하는 것은 아니다.
5. 탐색 종료 후 **평가·해석·권고·채택 판단을 쓰지 마라.** 설정, 모든 측정값, 오류, 실행 상태, 선택 규칙의 입력과 출력만 상세 MD에 남겨라.
6. 결과 MD와 재현 자료를 **기존 승인된 GitHub 저장소에 커밋·푸시하고 원격 반영을 확인하라.** 실제 MD 다운로드 링크까지 제공하라. 게시 실패를 성공으로 표현하지 마라.
7. 좋은 수치를 얻으려고 재실행을 추가하거나, 남은 예산으로 새로운 축을 임의로 확장하지 마라. 미사용 예산은 그대로 남겨도 된다.

## 2. 이번 차수에서 제외할 작업

다음은 `OUT_OF_SCOPE`로 기록한다. 이전 문서의 필수 항목이더라도 이번 범위가 우선한다.

| 제외 항목 | 이번 차수의 처리 |

| 무제한 프로파일링 | 기존 도구를 이용한 진단 최대 1회 |

## 3. 대조군과 최대 6개 탐색 구성

### 3.1 공통 조건과 사전 점검

모델·가중치·컨테이너·소스 revision을 동결한다. 기존 환경을 업데이트하지 않는다.

```text
GPU: H100 80GB ×4, 물리 index 0/1/2/3, TP4
CPU: 양 소켓, kt cpuinfer 96, threadpool 2, turbo OFF 유지
모델: Qwen/Qwen3-Coder-480B-A35B-Instruct-FP8
기존 모델 revision: 003f183a92fbe5b9a8325aaa8b2ae797c91dd90f
CPU expert: /models/kt/qwen3-480b-int4, AMXINT4
attention backend: triton
context length: 32768
EP dispatch: dynamic
prefill CUDA graph: disabled
speculative decoding: disabled
```

실제 모델·컨테이너 경로와 옵션 지원 여부는 현재 환경에서 확인한다. 전체 명령·환경변수·적용값·코드/바이너리 해시·GPU UUID를 저장한다. 의도하지 않은 `KT_*` 변수 상속을 제거한다.

수백 GB 모델을 매번 다시 해시하지 마라. 기존 snapshot·shard manifest를 재사용하고, 설정·hotmap·패치·실행 바이너리의 해시를 기록한다. 기존 하네스를 재사용하며 새로운 범용 프레임워크를 만들지 않는다.

### 3.3 탐색 셀

| ID | 부모 | 변경 내용 | 고정 조건 |

S2는 **hotmap 갱신과 층별 배치의 복합 변경**이다. 층별 배치만의 기여를 분리한 실험으로 표기하지 않는다. 새 recorder 수집이나 배치 알고리즘 개발은 하지 않는다. 기존 패치·JSON이 없거나 적용 불가하면 `BLOCKED_DEPENDENCY`로 종료한다. 실제 로드 결과에서 62층의 배치값과 합계5952를 확인한다.

S1은 실제 kt 워커 affinity를 확인한 뒤 남은 물리 코어와 그 HT 형제에만 적용한다. kt가 사용하는 물리 코어의 HT 형제를 비-kt 전용 코어로 잘못 사용하지 않는다. 적용된 TID별 affinity를 저장한다.

S3/S4/S5는 **이번 실험 후보**이며 개선을 보장하지 않는다. 설정이 실제 경로에 적용되지 않으면 `NO_EFFECTIVE_PATH`, 미지원이면 `UNSUPPORTED`로 기록한다. 대응을 위한 새 개발이나 버전 업데이트를 시작하지 않는다.

준비·출력 확인도 아래 별도 상한을 적용한다. 이를 성능 벤치 회수에 숨기지 말고 실제 실행량을 따로 보고한다.

| 항목 | 상한 |
|---|---|
| 서버 부팅 시도 | 14회: 대조군2＋탐색6＋부모 재확인2＋확인 대상 재시작2＋재시도2 |
| 워밍업 | 성공한 부팅당1회, C16·32요청, 최대14회 |
| 부팅 smoke | 기존 greedy4문항까지, 성공한 부팅당1세트 |
| 추가 출력 확인 | 기존 GSM40을 확인 대상 최대2개에 각1회, 최대80문항 |
| 프로파일링 | 위 진단1회 외에는 추가하지 않음 |

GSM 하네스가 없으면 새 의존성을 설치하지 않고 `BLOCKED_DEPENDENCY`로 기록한다. 준비·부팅·출력 확인 실패도 무한 반복하지 않는다. 상한은 완료 시간 예측이 아니라 실행량 통제 규칙이다.

### 4.2 실행 순서

```text
환경·입력 manifest·기존 패치 확인
 → B3/B4 각각2회
 → S1~S5 각각1회
 → 조건 충족 시 S6 1회
 → 계열별 확인 대상 고정
 → 필요한 부모 대조군 재확인
 → 대상A: 새 프로세스에서3회＋별도입력1회＋GSM40
 → 대상B: 새 프로세스에서3회＋별도입력1회＋GSM40
 → 같은 대상B에서 연속 부하, 필요 시 진단1회
 → 데이터 검증·MD 생성·GitHub 반영·다운로드 제공
```

연속 부하 대상은 확인 대상 고정 시 지정하고 마지막에 실행한다. 대상이1개뿐이면 해당 구성을 사용한다. 입력 변경·출력 확인처럼 재시작이 필요 없는 측정은 같은 서버에서 묶어 실행한다. 부팅 시 읽는 설정을 실행 중에 바꾸고 적용된 것처럼 처리하지 않는다.

같은 CPU·GPU·DRAM을 사용하는 성능 벤치를 병렬 실행하지 않는다. 무거운 로그 변환·압축·게시를 측정과 겹쳐 자원을 경쟁시키지 않는다.

## 5. 후보 선택과 종료 규칙

아래는 실험 진행을 위한 기계적 선택 규칙이며, 결과 보고의 평가 문장이 아니다.

1. 요청 전수 완료, 실제 설정 적용, NaN 등 구현 이상 없음이 확인된 실행만 확인 후보에 넣는다. 실패 원본은 삭제하지 않는다.
2. B3·B4 계열을 분리한다. 각 부모와 후보의 C64 출력tok/s 및 TTFT/TPOT p95를 기록한다.
3. 계열별 부모2회로 1차 선택 임계값을 고정한다. `delta = max(0.05, abs(parent_run1-parent_run2)/mean(parent_runs))`.
4. 부모 평균보다 처리량 증가율이delta를 넘는 후보를 확인 후보로 삼는다. 없으면 부모를 유지한다. 같은 계열에 여러 개면 처리량 순으로1개만 남기고 지연시간도 반드시 병기한다. **이 규칙은 유의성 검정·품질 판정·SLA 합격 기준이 아니다.**
5. S1/S3/S4/S5 중 조건을 만족한 변경이2개 이상이고 호환되면 S6를 만든다. 그렇지 않으면 `NOT_TRIGGERED`로 종료하고 중복 구성을 실행하지 않는다.
6. 확인 대상은 계열별 최대1개다. 각각3회 후에도 차이가 불명확하면 `UNRESOLVED_WITHIN_BUDGET`로 기록한다. 5회·9회로 자동 연장하거나 나쁜 반복을 버리지 않는다.
7. 새 후보가 없어도 범위 내 기록·출력 확인·파일 생성은 완료한다. 새로운 탐색 축은 자동 추가하지 않는다.

**종료 상태는 `BOUNDED_SEARCH_COMPLETE` 또는 `SEARCH_BUDGET_REACHED`를 기본으로 한다.** 전체 설정의 수렴·통계적 동등성·전역 최적을 확인했다고 쓰지 않는다. 등록한 모든 항목이 증거가 있는 종료 상태에 도달하면 이번 축소 범위의 실행을 마친다.

‘중간에 중지하지 말라’는 것은 옛 계획 전체나 무한 수렴 탐색을 실행하라는 뜻이 아니다. **이번 등록 범위의 처리와 최종 데이터 저장·게시 확인·전달을 포기하지 말라는 뜻이다.**

## 6. 비교 조건과 상세 데이터

### 6.1 측정 조건

- 주 벤치: C64·256요청·sonnet512입력/128출력·prefix100·request-rate inf. sampling·EOS·stop 조건을 고정하고 실제 token 수를 남긴다.
- 비교용 요청 manifest를 한 번 고정해 B3/B4와 모든 후보에 동일하게 사용한다.
- 매 반복 전 KV/prefix cache를 같은 방법으로 초기화하고 성공 응답을 저장한다. 워밍업 후에도 초기화한다. IDE_070의 flush 없는 반복과는 다른 조건임을 명시한다.
- 별도 입력 측정은 주 벤치와 요청ID가 겹치지 않는 manifest를 사용한다. 기존 hotmap 생성 입력과의 독립성을 확인할 수 없으면 `CALIBRATION_OVERLAP_UNVERIFIED`를 적는다. 다른 seed만으로 독립성을 입증했다고 쓰지 않는다.
- 부팅·워밍업·cache 준비·측정·drain 시각을 구분한다. 선행 단계 실패 시 일반 벤치를 시작하지 않는다.
- 일반 성능 측정에는 perf·py-spy·전체 expert recorder·동기 디버깅·매token 디스크 기록을 넣지 않는다.

### 6.2 저장 항목

**상세함은 실험 항목을 늘리는 것이 아니라, 수행한 실험의 원기록을 빠짐없이 남기는 것으로 확보한다.** 기존 하네스에서 다음 데이터를 수집한다.

```text
cell / parent / attempt / repetition / config hash / code·binary hash
전체 launch·bench 명령 / 인증정보를 제거한 환경변수 / effective config
시작·종료·경과 시간 / 부팅·graph 준비 시간
요청 성공·실패 수 / 실제 input·output tokens / 출력tok/s
요청별 TTFT·TPOT·E2E latency / 수집 가능한 ITL
TTFT·TPOT·ITL p50/p95/p99 (수집 불가이면 null과 이유)
기존 CPU·GPU·HBM·RSS 시계열 / cache 사용량
기존 로그의 retraction·recompute·queue·실제batch size
thread affinity / expert 배치 적용 결과
출력 텍스트·수집 가능한token ID / finish reason
오류 원문 / server 전체 로그 / exit code / timeout 이유 / 재시도 이력
```

기존 하네스로 얻을 수 없는 레이어별·expert별 시계열은 `NOT_COLLECTED`와 이유를 남긴다. 수집만을 위한 새 계측 패치는 만들지 않는다. 진단1회를 실행했다면 그 데이터·측정 창을 별도 첨부하고, 진단 중tok/s를 일반 평균에 섞지 않는다.

주 벤치·별도 입력·연속 부하·GSM40은 별도 표로 기록한다. 모든 반복 원값과 평균·중앙값·최소·최대·표본표준편차(ddof=1)를 남긴다. 1회 측정의 표준편차 및 실패로 누락된 지표는null이다. 서버 부재로 발생한0을 정상 성능 평균에 포함하지 않는다.

GSM40은 문항별 출력·정답·기계적 정오만 저장한다. ‘품질 동등’, ‘운영 가능’, ‘근사 경로 안전성 입증’ 같은 판단을 쓰지 않는다.

## 7. 복구·30분 보고·실행 지속

동일 장애의 재시도는 최대1회, 캠페인 전체 최대2회다. 코드 수정 캠페인으로 확장하지 않는다. 당해 실험의 프로세스만 정리한 뒤 다음 독립 셀로 진행한다.

부팅과 벤치에는 사전에 유한한timeout을 등록한다. 일반 부팅watchdog는600초, 일반 벤치는 `max(300초, 부모의 동일 부하 실행시간×5)`를 초기값으로 사용하고 실제 값을manifest에 저장한다. 이는 장애 감지 상한이지 완료 소요시간 예측이 아니다. 최초 컴파일 등에 별도 상한이 필요하면 실행 전에1회 한도를 등록한다.

Xid·ECC·열·전원 위험, 권한 부족, 다른 사용자 작업에 대한 간섭이 있으면 해당 실행을 차단한다. 안전·권한 제약을 무시하고 완주하지 않는다. 서버 전체가 이용 불가하면 취득 데이터와 미실행 목록을 보존하고 `BLOCKED_ENVIRONMENT`를 보고한다.

시작 후1800초마다 독립된 경량 루프가 `PROGRESS.md`에 아래를 기록하고, 승인된 전달 수단으로 사용자에게 보고한다.

```text
Asia/Seoul 시각 / 경과seconds / 현재cell·phase·repetition
일반 벤치 소비회수/20 / 진단·연속부하·재시도 소비회수
부팅 소비회수/14 / 완료·실패·blocked·미실행 수
직전 실측값 / 오류 원문과 경로 / 다음 등록항목
최신 저장파일 / 보고 저장상태와 실제 전달상태
```

전달 수단이 없으면 `REPORT_DELIVERY_UNAVAILABLE`로 기록한다. 파일 저장만으로 사용자에게 전달했다고 쓰지 않는다. 보고 실패 때문에 전체 실험을 중단하지 않는다. 종료 보고도 남긴다.

## 8. MD 저장·GitHub 게시·다운로드 제공

최소 산출물은 다음과 같다. 실제 디렉터리는 기존 프로젝트에 맞춰도 된다.

```text
PLAN_RESOLVED.md             # 범위·실제 설정·실행량 상한
PROGRESS.md                  # 30분 보고·상태 변화
FULL_REPORT.md               # 모든 설정·반복·실패·원데이터 참조
RESULT.md                    # 수치표·실행 상태·출처만
cells/<id>/                 # 명령·raw JSON·요청별 데이터·로그
selection_trace.jsonl       # 규칙ID·입력수치·확인대상·NOT_TRIGGERED
artifact_manifest.jsonl     # 파일명·크기·SHA256·저장 및 게시위치
PUBLISH_RECEIPT.md           # commit SHA·원격 확인·전달 및 접근 상태
```

`FULL_REPORT.md`에는 **부팅·준비까지 포함한 실제 전체 실행시간 내역과 계획/소비 회수**를 넣는다. 제외 범위를 옛 계획의 미완료 항목으로 되돌리지 않는다. 재시도·미지원·미수집도 빠뜨리지 않는다.

수렴 또는 이번 유한 탐색 종료 후에는 **평가·원인 추측·권장 구성·후속 제안을 쓰지 말고 측정 사실만 최대한 상세히 기록한다.** 표는cell/rep 순서로 두고 ‘최고’, ‘채택’ 같은 제목을 붙이지 않는다.

GitHub는 기존 승인된remote·branch만 사용한다. 무단 공개 저장소 생성·force push·인증정보/개인정보/모델 가중치 게시를 금지한다. 큰raw파일은 승인된 위치와SHA256을MD에서 참조한다. commit·push 후remote의SHA와대상MD 존재를 확인한다. 권한 오류가 발생하면 그 원문을 보존하고 게시 성공으로 표현하지 않는다.

마지막에는 **실재하고 접근이 확인된 MD 다운로드 링크**를 제공한다. 파일 경로만 쓰거나 ‘GitHub에 있다’고 말하는 것으로 대체하지 않는다. 최종 답변은 아래 사실만 포함한다.

```text
실행 상태와 완료/실패/blocked/미실행 수
실제 소비 벤치·부팅 회수
GitHub 반영 상태·commit SHA·파일 위치
MD 다운로드 링크·raw 데이터 위치
```
