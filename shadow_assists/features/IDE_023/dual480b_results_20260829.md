# 480B 모델 2개 동시 서빙 실험 결과 (2026-08-29)

> 한 문장 요약: **GPU 8장짜리 머신 한 대에서 480B 모델 두 개를 동시에 서빙했고, 서로 간섭은 사실상 0이었다. 부하를 맞춘 비교에서 분할 구성이 통합 구성보다 전 부하 구간 +2~12% 높다.**
>
> ⚠ 정정 (2026-08-29 K3): 본문 표의 "+37%" 는 부하 불일치 비교 (D 총부하 32 vs S 총부하 16) 였다. 부하-정합 재측정 결과는 `eval/results/20260829_175150_k3_crossover/RESULTS.md` — D 우위는 유지되나 폭은 +2~12%.

## 1. 실험 구성

| | 인스턴스 A | 인스턴스 B |
|---|---|---|
| 모델 | Qwen3-Coder-480B-A35B (FP8 원본 450GB) | 동일 모델, 별도 인스턴스 |
| GPU | 0–3 (4장) — attention·KV 담당 | 4–7 (4장) |
| CPU | 소켓0, 48스레드 — expert 연산 (AMX, INT4 232GB) | 소켓1, 48스레드 |
| 메모리 | NUMA0 | NUMA1 |
| 격리 방식 | 전용 컨테이너 + cgroup cpuset (코어·메모리 노드 고정) | 동일 |

참고: 두 인스턴스는 같은 INT4 가중치 파일(232GB)을 mmap으로 공유하므로, DRAM은 두 벌이 아니라 **한 벌 분량만** 쓴다. GPU 단독으로는 이 모델을 4장에 올릴 수 없다(OOM 실측 — 480GB > HBM 320GB).

## 2. 결과

| 측정 | 단독 실행 | **동시 실행 (4+4)** | 간섭 |
|---|---:|---:|---:|
| A 처리량 | 30.4 tok/s | **30.59 tok/s** | **≈ 0%** |
| B 처리량 | 31.0 tok/s | **30.58 tok/s** | **≈ 0%** |
| TPOT (토큰당 지연) | ~420 ms | 418 / 414 ms | 동일 |
| CPU 사용률 | 22.8% (1개 기준) | **45.1%** | 두 소켓이 실제로 병렬 가동 |
| **머신 합산 처리량** | — | **61.2 tok/s** | 단일 인스턴스 최고 구성(GPU 4장+CPU 96스레드, 44.5) 대비 **+37%** |

부하: 인스턴스당 64요청 × 동시 16, sonnet 512/128, 3회 계열 실측 재현 일관. 모든 수치는 CPU 터보 꺼진 상태(2.0GHz)의 하한값이다.

**비교 기준에 관한 주의**: "GPU만 8장" 구성과의 비교는 없다 — 이 모델은 GPU-only로 TP=4는 OOM, TP=8은 엔진의 FP8 블록 양자화 제약으로 부팅 자체가 불가해(둘 다 실측) 그런 기준선이 존재하지 않는다. +37%의 비교 대상은 GPU 4장+CPU 96스레드를 한 인스턴스에 몰아준 hybrid 구성(44.5 tok/s)이다. hybrid TP=8+96스레드(전체 머신 1-인스턴스) 기준선은 미측정 항목으로 남아 있다.

### 왜 합산이 +37%인가

CPU expert 연산은 스레드를 늘려도 성능이 비례로 늘지 않는다(메모리 대역폭 한계). 96스레드를 한 인스턴스에 주면 44.5 tok/s지만, 48스레드씩 두 인스턴스로 나누면 각 30.6씩 총 61.2가 나온다. **자원을 쪼개서 인스턴스를 늘리는 쪽이 머신 전체로는 더 많이 뽑는다.**

## 3. 도달 과정에서 잡은 문제 (중요)

처음 동시 실행은 인스턴스당 **1.6 tok/s로 붕괴**(단독의 5%)했다. 원인을 3단계 실험으로 좁힌 결과:

- 컨테이너를 나눠도, 가중치를 나눠도 재현 → 공유 자원 문제 아님
- 소켓별 사용률 실측에서 확정: **kt-kernel의 CPU 스레드가 numactl 지시를 무시하고 항상 절대 0번 코어부터 고정 배치**된다. 두 인스턴스의 96스레드가 소켓0의 56코어에 몰려 경합했고, 한쪽은 자기 메모리를 원격 소켓 너머로 읽고 있었다
- **해결: 컨테이너 자체를 cgroup cpuset으로 소켓에 가둔다** (`--cpuset-cpus`, `--cpuset-mems`) — 어떤 스레드 고정 시도도 밖으로 못 나간다. 적용 즉시 간섭 0으로 회복

이 결함은 kt-kernel(KTransformers) 업스트림에 제보할 가치가 있는 발견이며, 다중 인스턴스 배치 시 위 격리는 필수 절차다.

## 4. 재현

- 가중치 변환(1회): `kt quant <FP8 스냅샷> -m int4 -i fp8 -o <출력> --cpu-threads 96 --numa-nodes 2 -y`
- 인스턴스 B 컨테이너: `docker run ... --privileged --cpuset-cpus "56-111,168-223" --cpuset-mems "1" ...` + 호환 패치 적용 스크립트(`setup_kt_container.sh`)
