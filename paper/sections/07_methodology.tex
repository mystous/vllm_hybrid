\subsection{모델}

7B부터 671B까지 3계열 $\times$ dense/MoE 10개 모델을 측정한다:
Qwen-2.5 7B/32B/72B, Llama-3.1 8B/70B, Llama-3.1-405B-FP8,
DeepSeek-R1-Distill-Qwen 7B/32B, DeepSeek-R1-Distill-Llama-70B,
그리고 \textbf{DeepSeek-R1 671B (MoE 추론)}.
이로써 (i) 크기(7B--671B), (ii) 계열(Qwen/Llama/DeepSeek),
(iii) 유형(dense vs MoE, 표준 vs 추론 특화)을 분리한다.

\subsection{워크로드: 실 서빙 trace}

합성 데이터 대신 6종의 공개 실 trace 를 prompt 소스로 사용한다:
대화 계열 \textbf{ShareGPT}, \textbf{WildChat}, \textbf{LMSYS-Chat-1M},
코드 계열 \textbf{SWE-bench}, \textbf{MBPP}, \textbf{HumanEval}.
각 corpus 에서 마지막 user turn / problem statement / prompt 를 추출하고
sha1 정규화 dedup 및 길이 필터($32\le\text{tok}\le4096$)를 적용한다.
\textbf{mix} 조건은 6 corpus 를 교차 셔플한 별도 샘플로,
단일 서버에 이질 트래픽이 혼재하는 운영 상황을 모사한다.

\subsection{방법과 측정 시나리오}

\textbf{방법(4종).} vanilla(투기 없음) / suffix(SuffixDecoding, $K=32$) /
ngram(prompt-lookup) / llm-d(라우팅).

\textbf{시나리오 1 — 처리량 oracle.}
각 모델을 단일 인스턴스(TP=8, 7B급 TP=4; XL 405B/671B 는 8-GPU)로 기동하고
방법별로 동일 prompt 를 조건별 측정한다
(concurrency 32, \texttt{max\_tokens}=8{,}192, streaming).
방법별 per-prompt 처리량으로 (모델, 조건) oracle(최적 방법)을 산출한다.
정확도는 vanilla 와 suffix 출력 텍스트의 분포 동등(losslessness)으로 확인한다.

\textbf{시나리오 2 — llm-d 라우팅.}
vanilla 와 suffix 두 백엔드를 동일 GPU 예산으로 분할
(8-GPU 모델 $=2\times$TP4)한 뒤 llm-d Gateway 가 load/prefix-aware 라우팅을 수행하고,
kind 기반 Kubernetes 에 vLLM pod 를 배치해 동일 부하(conc=32)로 비교한다.

\subsection{지표}

셀별로 output\_tps, TTFT/TPOT(p50/p99), suffix accept rate $\alpha$,
GPU/CPU 이용률(UtilSampler 동기), GPU 메모리를 수집한다.
방법-이득 $\Delta$(Def.~\ref{def:method-gain})와 (모델,조건) oracle 을 파생한다.

\subsection{커버리지와 한계 (정직)}
\label{subsec:coverage}

주력 8모델은 4방법 $\times$ 7조건 전수, XL 2모델(405B/671B)은
vanilla/suffix/llm-d $\times$ 7조건이다(XL ngram 은 제외).
단일 corpus 조건은 해당 corpus 샘플 전수(164--500), mix 는 별도 500 샘플이므로
mix 절대 tps 를 단일 corpus 와 직접 비교하지 않는다.
naive ngram 은 Qwen-7B 에서만 전 corpus 측정했고(붕괴 확인),
eagle 계열은 본 연구 범위 밖이다.
모든 raw(per-request 로그$\cdot$summ$\cdot$parquet)는 보조 자료로 공개한다.
