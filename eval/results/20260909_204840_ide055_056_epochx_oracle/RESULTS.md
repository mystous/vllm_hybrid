# EPOCH-X 1단계 trace oracle — IDE_055 (EHES) / IDE_056 (SER) — **둘 다 문서 게이트에서 조기 기각**

문서(`3d543f0c-epoch_02.md`) 지시: "full serving stack 을 수정하기 전에 기존 routing trace 로 oracle simulation 을 먼저 하고, oracle 이 이긴 영역만 코드로 옮긴다."

입력: 실측 라우팅 트레이스 `/tmp/expert_distribution_recorder_alpha_0.pt` (399 패스 × 62층 × 160 expert, hot-96 α0.25 map 아래 수집).
상수 (2026-09-09 실측, `KT_AVX_RB=1 KT_AVX_PF=2`): expert 당 CPU = 고정 8 µs + 스트리밍 58 µs + 행당 9.5 µs (m=1 에서 66 µs, 스트리밍 비중 88%), 층당 핸드오프 130 µs, expert INT4 23.6 MB.
모델 타당성 확인: 오라클의 스텝당 CPU 50.4 ms vs 같은 체제의 실측 TPOT 57.6 ms (C64) → CPU 가 스텝의 87%. 일관.

## IDE_056 — SER (CPU slice 만 독립 요청 간 rendezvous)

| 항목 | 값 |
|---|---|
| 현행 rows/weight-read | **평균 1.582**, 중앙값 1, p90 3 (read 200,447건) |
| 다음 decode 스텝 도착까지 | **50.4 ms** (문서의 `W_max` 500 µs 의 **100배**) |
| cohort skew S=1 / 2 / 4 | rows/read 1.582 → **1.181 / 1.077 / 1.023**, 층당 CPU +39% / +64% / +101% |
| (참고) prefill 행이 합류하는 혼합 forward | rows/read **24.5** (15.5×) |

판정: **기각**. 문서 게이트는 "TPOT p99 +5% 이내에서 rows/read ≥ 1.7". decode 는 이미 lockstep 배치라 배치 안의 모든 독립 요청 행이 한 read 에 합쳐져 있고, 더 모으려면 다음 스텝(50 ms)을 기다려야 해 TPOT 예산을 100배 초과한다. cohort 를 쪼개는 skew 는 같은 expert 를 여러 번 읽게 만들어 오히려 행 수를 낮춘다. **SER 이 노리던 기전(read 당 행 증가)은 이미 채택된 혼합 forward(IDE_052)가 rows/read 24.5 로 달성**하고 있다.

## IDE_055 — EHES (expert 를 channel 로 분해해 CPU·GPU 분수 배치)

층당 CPU 기대 시간 = Σ_e p_e [ 8·1{ρ_e<1} + (58 + 9.5·m̄_e)(1−ρ_e) ], 제약 Σ_e ρ_e ≤ M (expert 단위, 동일 VRAM 예산).

| 배치 전략 (M=96 동일 예산) | 층당 CPU µs | greedy 대비 | 층당 CPU 스트리밍 MB |
|---|---|---|---|
| **greedy full-expert (현행)** | **611.3** | — | 179.5 |
| 최적 분수 배치 (fractional LP) | 611.3 | **+0.0%** | 179.5 |
| 상위 112개에 ρ=0.857 균등 | 2205.5 | +260.8% | 333.7 |
| 상위 128개에 ρ=0.75 균등 | 3105.9 | +408.0% | 497.8 |
| 전체 160개에 ρ=0.6 균등 | 4526.2 | +640.4% | 780.8 |

예산 frontier (이산 vs 연속):

| M (expert) | greedy 층당 µs | M+0.5 분수 |
|---|---|---|
| 80 | 1275.4 | 1252.9 |
| 88 | 908.6 | 890.0 |
| 92 | 751.2 | 734.6 |
| **96 (현행)** | **611.3** | 596.9 (**−2.4%**) |
| 100 | 488.4 | 475.5 |

판정: **기각**. 문서 게이트는 "동일 VRAM 예산에서 makespan −10~15% 이상". 목적함수가 ρ 에 선형이고 제약이 바이트 예산 하나뿐이라 **최적해가 꼭짓점(=greedy full 배치)**이며, 분수 배치의 이득은 0.0% 다. 예산을 여러 expert 에 얇게 펴는 방식은 "cold 채널이 조금이라도 남은 expert마다 고정비 + 잔여 스트리밍"을 그대로 물기 때문에 CPU 시간이 2.6~6.4배로 악화된다. 이산성(半 expert 단위) 완화 이득은 최대 **−2.4%** 로 게이트의 1/6 이하다.

부수 확인: 층당 CPU 시간은 예산 M 에 매우 민감하다 (96 → 100 에서 −20%). 즉 이 시스템에서 유효한 축은 "expert 를 쪼개는 것"이 아니라 **GPU 에 상주하는 expert 를 늘릴 VRAM 을 확보하는 것**이며, 그 VRAM 을 KV 에서 빼는 거래는 이미 IDE_040 에서 손해로 측정되었다.

## 종합

문서의 EPOCH-X 세 축 중 두 축(EHES 공간 분해, SER 시간 집약)은 **구현 전 오라클 단계에서 기각**된다. 남은 축은 GRC(층당 잔여 고정비 제거)이며 문서 자신이 Amdahl 상한을 +8.7%, 현실 목표를 +3~7% 로 잡았다 → 다음 단계로 이 고정비의 구성 요소를 계측한다 (IDE_057).
