# IDE_048 — AVX-512 vec 경로 (decode 1~2행) 레지스터 블로킹 — **부분 채택** (커널 효율·bit 동일, 서빙 소폭)

원본 `GemmKernel224Int4::avx_kernel`: 누산기 `c512[]` 가 메모리, 행마다 B 언팩 반복 → dpbssd 체인 latency-bound.
새 커널 `avx_kernel_rb` (`KT_AVX_RB=1`): k-group 당 B 4벡터 1회 언팩, 8/4/2/1 행 블록 누산기를 zmm 에 유지, 1행은 4분할·2행은 2분할 K 누산기 (체인 8개). 정수 누산 → **bit 동일** (T=8/40/200 n_cold 8, T=1024 n_cold 64: max abs diff 0).

- 행당 한계 비용 (32 expert, 1→16행): 13.5 → 9.5 µs (−30%). 사전 등록 (−50%) 미달. 남은 9.5 µs 는 AVX-512 VNNI 피크의 ~40% 수준.
- 1행 (decode 지배 케이스): 75 → 69 µs = 소켓당 스트리밍 165 → ~180 GB/s (torch 96스레드 읽기 195 GB/s 에 근접). 누산기 체인이 적재 발행을 막던 몫이 일부 있었음.

## 서빙: 최선 구성 + `KT_AVX_RB=1`

|---|---|---|---|
| 새 커널 | **975.9 / 118.1 / TTFT 5.97s** | **781.9 / 59.8 / 2.87s** | 97.5 |

→ C160 변화 없음 (decode 평균 행 수 1.1~1.3 이라 행당 비용 절감이 스텝에 거의 안 드러남), C64 +2~7% (오늘 최고 C64).
EAGLE3 구성 재측정 (KV 87k): C160 698.2 / 188.9, 수락 길이 2.0~2.3 → IDE_047 과 동일 (검증 스텝은 GPU 투기 오버헤드 + cold expert 수 2배가 지배).

판정: 커널은 bit 동일·효율 개선 (1행 −8%, 16행 −24%) 이라 **기본 켬으로 채택** (`KT_AVX_RB=1`). 서빙 이득은 C64 에서만 소폭. 사전 등록 기준 (행당 −50%, C160 +8%) 은 미달.
