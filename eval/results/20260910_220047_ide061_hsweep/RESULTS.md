# IDE_061 — hot expert 수 H 재탐색 (1단계)

**착수 근거**: EXP-E03 물리 계측에서 서빙 중 DRAM 읽기가 이론 천장의 36~48% 에 머물러 대역폭이 절반 이상
남아 있었다. H 를 줄이면 (a) GPU 가중치 메모리가 풀려 KV 풀이 커지고 (b) CPU 가 맡는 expert 가 늘어난다.
IDE_058 에서 처리량 이득의 경로가 KV 용량 → 동시성 임이 확인됐으므로 두 방향 모두 목표에 부합하는 것으로 보였다.

측정: 2026-09-10 22:00~22:34. hot map 은 빈도 내림차순이라 `--kt-num-gpu-experts` 만 바꾸면 상위 H 가 GPU 에 남는다.
`--max-total-tokens 143360` 유지 (그래서 H=80/64 의 KV 는 이 상한에 걸렸다 — 아래 2단계 참조).

## 판정 — 기각. H 를 줄이는 방향은 손해다

1. **단조 감소이고 폭이 크다.** expert 16개를 CPU 로 넘길 때마다 같은 동시성에서 처리량이 약 1/3 씩 깎인다
   (C64: 781.8 → 518.6 → 344.1, C224: 1085.1 → 756.4 → 532.4).
2. **KV 풀이 더 커도 소용없다.** H=80/64 의 KV 는 143,360 토큰으로 H=96 의 127,309 보다 12.6% 크지만
   처리량은 30~51% 낮다. GPU 메모리가 장치당 10.6~21.8 GB 풀린 이득보다 CPU 전가 비용이 압도적으로 크다.
3. **대역폭 여유는 원인 진단을 오도했다.** 토큰당 물리 읽기는 202.6 → 306.9 → 462.7 MB 로 2.3배 늘지만
   실제 대역폭 사용은 219.8 → 246.4 GB/s 로 12% 만 늘고 이론 천장의 44% 에 머문다.
   처리량이 그만큼 떨어지기 때문이다. **CPU expert 경로는 대역폭이 아니라 대기·연산에 묶여 있다.**
   따라서 "대역폭이 남으니 CPU 에 더 넘길 수 있다" 는 가설은 **기각**한다.
4. **반대 방향 (H=112) 은 메모리가 막는다.** mem-fraction-static 0.94 에서 부팅 실패
   (장치 3 에서 880 MB 요구, 여유 748 MB). H=96 이 이미 장치당 78.9 GB 를 쓰고 있다.

## 함의

- 이 모델·이 구성에서 **H=96 은 이미 상한 부근의 좋은 선택**이며, 과거 hot-96 > hot-80 판정
  (bf16 KV·동시성 32 조건, 458.9 대 319.9) 은 fp8 KV·높은 동시성에서도 유지된다.
- CPU 로의 expert 전가는 **선택이 아니라 전제**다 (480B 전체 expert 를 4 GPU 에 올릴 수 없다).
  판정 대상은 전가량이고, 측정은 "가능한 한 적게" 를 가리킨다.
- 개선 지점은 읽는 바이트를 늘리는 쪽이 아니라 **기다리는 시간을 줄이는 쪽**이다 (층 인계·겹침).
  IDE_057 (층당 잔여 고정비 130 µs) 이 계측 게이트에서 기각된 이력이 있으므로, 다시 열려면
  새 기전이 필요하다.
