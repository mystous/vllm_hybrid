# IDE_066 — NaN 발생 지점 계측 (KTransformers MoE 합산 지점)

`IDE_063`/`IDE_064` 에서 NaN 사망의 원인 축을 특정하지 못했다 (KV dtype·지연 expert·누적 이력·
mixed forward 모두 기각). SGLang 의 비-투기 경로에는 NaN 검사가 샘플러 한 곳뿐이라
`kt_ep_wrapper.apply()` 의 합산 직전에 CPU/GPU expert 출력을 따로 세는 계측을 넣었다
(패치 `eval/harness/20260910_e12/kt_nan_probe_patch.py`, 환경변수 `KT_NAN_PROBE=1` 로만 동작).

측정: 2026-09-11 08:53~10:0x. EPOCH-OPS 구성 + 완화, 도착률 5.0 × 3,000요청 × 4회.

## 층별 NaN — CPU 와 GPU 가 항상 같다

4회 누적 (모델 62층, 층 0~6 은 기록 없음 = NaN 0건):

| 층 | CPU expert NaN | GPU expert NaN |
|---|---|---|
| 0~6 | **0** | **0** |
| 7~22 | 1 | 1 |
| 23~41 | 2 | 2 |
| 42~59 | 3 | 3 |
| 60~61 | 4 | 4 |

같은 기간 샘플러 치환 4건 (4랭크 동시 1회).

## 판정 — KTransformers 의 CPU expert 경로는 원인이 아니다

1. **모든 층에서 CPU 와 GPU 카운트가 정확히 일치한다.** 두 경로는 같은 입력 `x` 를 받아 각자 계산한다.
   NaN 이 CPU expert 안에서 (INT4 역양자화·AMX 커널) 생겼다면 그 층에서 CPU 쪽만 NaN 이고
   GPU 쪽은 깨끗해야 한다. 양쪽이 동시에 NaN 이라는 것은 **이미 NaN 인 입력을 받아 흘려보냈다**는 뜻이다.
2. **층 0~6 은 깨끗하고 7층부터 나타난다.** 트랜스포머 블록 순서가 attention → MoE 이므로,
   6층 attention 이 원인이면 6층 MoE 출력도 오염됐어야 한다. 그렇지 않으므로 최초 발생 지점은
   **7층의 MoE 이전 (7층 attention 또는 6층 잔차 합)** 이다. 이는 GPU 측 계산이다.
3. 깊은 층일수록 누적이 커지는 것 (1 → 4) 은 한 번 오염된 요청의 상태가 이후 스텝에서도 NaN 인 채
   유지되기 때문으로 보인다.

**본 프로젝트 관점의 결론: CPU expert 코드는 NaN 의 원인이 아니다.**

## 한계

- 계측이 `tp_rank == 0` 안에만 있어 나머지 세 랭크의 GPU expert 출력은 보지 못한다.
  logits 는 랭크 간 공유되므로 어느 랭크에서 나든 4랭크 모두 치환된다.
- "층 0~6 기록 없음" 은 1판이 NaN 0 일 때 기록을 남기지 않는 설계라서이며, 7~61층이 동시에
  `calls=2000`·`6000` 으로 보고된 것으로 미루어 0~6층도 점검은 됐다고 본다 (직접 확인은 아님).
- 위 두 한계를 고친 2판 패치 (`kt_nan_probe_patch2.py`: 심장박동 기록 + 전 랭크) 를 만들어 뒀으나
  **실행하지 않았다** (계획서 범위 밖 작업을 중단).
